# 미리보기 배포 운영 가이드

## 배포 흐름

| 계기 | 확인하는 값 | 결과 |
| --- | --- | --- |
| 같은 저장소의 PR을 main 대상으로 열거나 다시 열기, 새 커밋 또는 대상 브랜치 변경 | 현재 PR의 전체 SHA, 실제로 빌드한 이미지의 루트와 EKS 접두 경로에서 health·environment·version | 통과한 이미지 아카이브를 하루간 보관 |
| PR 빌드 완료 | 신뢰된 기본 브랜치의 빌드 정의, PR·대상 브랜치의 빌드 입력, 아카이브의 출처, 발행 서명 | GHCR 이미지와 서명 영수증, 해당 SHA의 준비 상태, preview 라벨 |
| 발행 성공, PR 상태 변경, 15분 예약 또는 수동 조정 | 현재 PR, 영수증 서명, 레지스트리 manifest, 상태 브랜치 기준 커밋 | 검증된 이미지와 차트를 한 쌍으로 기록. 새 이미지가 준비되는 동안 기존 배포를 유지 |
| main 변경 또는 명시적 발행 복구 | 필수 CI, 실행 아카이브, 발행 전 서명한 이미지 정보, 현재 소스와 배포 브랜치 끝 | 검증된 차트 트리와 다이제스트를 main-deploy에 승격 |

제목·본문만 편집하면 새 이미지를 만들지 않는다. PR의 빌드 정의나 빌드 레시피를 바꾸는 변경은 신뢰 경계를 바꾸므로, 리뷰 중인 브랜치에서 일반 CI가 성공해도 기존 기본 브랜치 발행기가 미리보기 발행을 보류할 수 있다. 새 정의를 도입한 뒤 기존 PR은 기본 브랜치를 반영해 재빌드한다.

같은 저장소에서 PR을 닫거나 대상 브랜치·라벨을 변경하면 `pr-lifecycle.yml`이 저장소 권한과 코드 체크아웃 없이 완료 신호를 보낸다. 기본 브랜치의 `preview-state.yml`은 GitHub API에서 실제 PR 상태를 새로 조회한다. PR 작업에서 지정한 번호·파일을 정리 대상으로 받지 않는다. 기존 슬롯은 신호 처리 시 확인하고, 슬롯이 없던 PR의 종료는 상태 브랜치에 저장한 마지막 확인 시각부터 후속 스캔으로 발견한다. 포크, 병합 충돌 또는 누락된 신호도 15분 예약 스캔에서 다시 확인한다. GitHub 예약과 대기열 지연만큼 반영이 늦어질 수 있다. 이 경로는 공개 저장소에서 2026년 12월 2일 기본 차단되는 `pull_request_target` 권한 예외가 필요 없다. [GitHub의 이벤트 정책 변경](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/)

## 배포 전용 신원과 브랜치 보호

1. 저장소 관리자는 기존 main, main-deploy, preview-state의 끝 커밋과 활성 배포 상태를 기록한다. preview-state는 기존 전용 상태 브랜치에서 시작한다. 새 설치라면 상태 파일 없는 초기 커밋으로 준비한다. 두 배포 브랜치 외에 기본 브랜치 자체의 필수 리뷰·CI와 우회 권한도 확인한다.
2. 저장소 콘텐츠 읽기·쓰기 권한을 가진 전용 GitHub App을 이 저장소에 설치한다. preview-publish 환경은 기본 브랜치 main에서만 사용할 수 있게 설정한다. 이 환경에 PREVIEW_WRITER_APP_ID 변수와 PREVIEW_WRITER_PRIVATE_KEY 비밀을 둔다. 설치 토큰은 Git 쓰기 단계에서만 사용한다. 기본 워크플로 토큰이 이미지·라벨·상태·서명을 담당하므로 기존 github-actions[bot] 영수증 검증을 이어갈 수 있다.
3. 아래 명령으로 규칙 두 개의 본문을 검토한다. APP_ID는 설치 번호가 아닌 앱의 숫자 ID다. RECOVERY_TEAM_ID는 배포 브랜치에 일반 커밋으로 복구할 팀이며 생략할 수 있다. writers는 생성·갱신을 지정 신원에만 허용한다. history는 우회 주체 없이 강제 갱신·삭제를 막는다. 격리된 시험 저장소 또는 시험 ref에서 일반 계정의 쓰기 거부, 앱의 일반 갱신 성공, 강제 갱신 거부를 확인한 뒤 관리자가 두 규칙을 생성한다. 생성 시 기존 동명 규칙이 있으면 중복 생성하지 말고 내용을 비교한다.
4. 생성 후 규칙을 수정할 권한이 있는 관리자 계정으로 approve를 실행한다. 활성 규칙의 실제 대상·우회 목록과 두 브랜치에 적용된 규칙 ID가 맞을 때만 출력되는 한 줄을 preview-publish 환경의 PREVIEW_APPROVED_RULESETS 변수에 저장한다. 워크플로는 토큰 발급 전에 두 규칙의 ID와 마지막 수정 시각, 각 브랜치에서의 적용 상태를 재확인한다. 나중에 우회 주체나 규칙을 바꾸면 재승인이 필요하다.

```sh
node scripts/deployment-rules.mjs writers "$APP_ID" "$RECOVERY_TEAM_ID"
node scripts/deployment-rules.mjs history "$APP_ID"
# 관리자가 검토한 두 규칙을 GitHub에 구성한 뒤 실행
node scripts/deployment-rules.mjs approve ASBG-PReview/PReview "$APP_ID" "$RECOVERY_TEAM_ID"
```

복구 팀을 지정하지 않을 때에는 해당 인수를 통째로 생략한다. 앱 키를 일반 저장소 비밀이나 PR 실행 환경에 복사하지 않는다. GitHub는 규칙 수정 권한이 있는 조회에만 우회 목록을 반환한다. [브랜치에 적용되는 규칙과 우회 주체 조회](https://docs.github.com/en/rest/repos/rules) · [설치 토큰의 저장소·권한 범위](https://github.com/actions/create-github-app-token)

## PR 배포, 종료, 이미지 보존

- preview-state의 `previews/pr-N/state.json`은 슬롯 기록이고 `deployments/pr-N/state.json`은 ApplicationSet이 읽는 배포 입력이다. 정규 레코드의 prNumber, commitSha, imageDigest, chartRevision은 문자열이다. 검증된 다이제스트와 차트 전체 SHA를 같은 Git 커밋으로 양쪽에 쓴다. 한쪽이 손상되면 정상본과 Git 이력을 확인한다. 증거가 부족한 슬롯은 보류하고 독립된 PR의 처리는 계속한다.
- 기본 슬롯 수는 2다. PREVIEW_MAX_SLOTS로 클러스터 여유에 맞춰 신규 배정을 제한할 수 있다. 0은 신규 배정을 멈춘다. 한도를 낮춰도 기존 배포를 해제하지 않는다. 실행 중인 워크로드, 롤링 중 추가 Pod와 실제 quota를 별도로 확인한다. 이미지 존재 표시만으로 슬롯 배정이나 Pod 준비를 판단할 수 없다.
- 처음 적용할 때는 새 작성기를 먼저 실행한다. `node scripts/reconcile-preview-state.mjs ASBG-PReview/PReview --check-projection`으로 기존 슬롯과 배포 입력을 모두 대조한 후 ApplicationSet의 감시 경로를 바꾼다. 알려진 구형 입력은 확인된 소스·다이제스트·차트 조합만 이관한다. 나머지는 새 빌드 근거와 이미지가 준비될 때까지 원래 슬롯을 보존한다. 설치와 장비별 인수 절차는 [Argo CD 가이드](../argocd/README.md)에 있다.
- PR 종료 시 두 활성 파일을 빼고 `cleanup/pr-N.json`에 이전 정상 상태, 실제 종료 시각, Git에서 내린 시각을 함께 기록한다. 두 시각 중 늦은 쪽부터 24시간을 보장한다. 보존 기간 안에 재오픈하면 기존 배포와 빈 자리를 대조해 복원한다. 다른 브랜치로 대상을 바꾼 열린 PR은 배포 대상에서 제외하며 이미지는 종료 사실을 확인한 뒤 정리한다.
- 정리 작업은 실제 종료 시각과 티켓의 blob SHA가 일치해야 한다. main의 현재 및 직전 서로 다른 이미지, 다른 PR의 배포, 유예 중인 상태, 태그 없는 인덱스까지 포함한 보존 이미지의 하위 manifest를 보호한다. 해당 PR의 정규 태그만 있는 버전이 후보가 된다. 삭제 직전마다 패키지 목록·대상 버전·두 배포 ref·PR을 재확인한다. 참조가 남거나 조회가 불완전하면 티켓을 남긴다. 완료 기록 도중 실패해도 다음 실행이 남은 목록부터 다시 계산한다.
- 예약 스캔은 활성화 이후 누락된 종료를 확인한다. 활성화 전 종료된 특정 PR의 회수가 필요하면 수동 입력 cleanup_pr로 지정한다. 수동 실행 기본값 dry_run=true는 유예가 지난 티켓과 삭제 계획만 조회한다. dry_run=false로 실행하면 상태를 조정하며 유예가 지난 요청만 회수한다. GitHub와 GHCR의 쓰기는 서로 독립적이다. 레지스트리 로그인에 실패해도 Git의 PR 종료 처리는 시도한다.

## main 복구와 인수

동일 소스와 동일 배포 트리의 재실행은 배포 ref를 다시 쓰지 않는다. 같은 SHA의 태그에 이미 검증된 이미지가 있으면 서명 근거를 확인한 후 재사용한다. 다른 다이제스트를 가진 기존 태그의 출처를 확인할 수 없으면 정지한다. 일반 수동 CI는 발행하지 않는다. 아카이브가 만료됐을 때에는 CI 수동 실행에서 main과 publish_current_main=true를 명시해 현재 소스를 재검증한다.

복구 담당자는 main-deploy의 이전 정상 차트와 이미지 파일을 함께 복원하는 일반 커밋을 만든다. 예를 들어 커밋 제목을 ‘이전 정상 배포로 복구’로 작성한다. 이 수동 커밋은 이후 자동 승격을 보류한다. 운영자가 재개하려면 main-deploy의 현재 끝에서 빈 승인 커밋을 만들고, 첫 줄을 정확히 `main 배포 재개 <현재 main 전체 SHA> <승인한 sha256 다이제스트>`로 쓴다. 해당 소스·이미지를 재확인하고 위의 발행 복구를 실행한다. 강제 푸시로 이력을 되돌리지 않는다.

인수 시에는 main과 서로 다른 두 PR 각각에 대해 Git의 소스·차트 SHA와 이미지 다이제스트, 실제 Pod의 준비 상태·이미지 ID, 외부의 health·environment·version 응답을 대조한다. 한 PR을 닫고 다른 PR과 main의 응답이 유지되는지, 유예 중 재오픈과 최종 종료 뒤 해당 리소스 회수가 각각 동작하는지 확인한다. 운영 관리 권한·실제 클러스터에서만 확인할 수 있는 이 결과는 PR 테스트와 별도로 기록한다.
